HYBRID Telescope Control is a Windows application for operating an amateur telescope by voice. A command such as "slew to M31, plate solve, and start imaging for 90 minutes" is carried out as a sequence of mount and camera operations. It is not intended to replace established imaging suites such as NINA or SGP. Its interaction model is different: voice-first control, combined with AI tool orchestration through the Model Context Protocol (MCP).

Development started in late 2024. By June 2026 the codebase comprised 200+ C# source files, 347+ unit tests, 47 MCP tools and 55+ voice actions, and a security audit had been completed in nine commits. This article summarizes how the project reached that state.

Why Voice Control?

The starting point was practical: operating telescope software at -5°C while wearing gloves is awkward. Each click means removing a glove, finding the right menu and hitting a small target, then putting the glove back on. Voice control addresses this directly and improves usability in the observing workflow, beyond simple convenience.

Simple voice commands are not sufficient on their own. A wake-word system that responds to "Hey Telescope" can handle "go to M31" but not "slew to M31, plate solve, center it, autofocus, and start imaging for two hours with 180-second exposures." Multi-step commands require an AI model that can plan the sequence. The Model Context Protocol, introduced by Anthropic in 2024, provides a standard way for an AI assistant to discover and call telescope tools.

The Timeline

Late 2024

Project Start

First commit. Basic ASCOM mount control, WPF UI, no voice. Voice commands were planned from the start.

Early 2025

Voice Pipeline

Python voice bridge with faster-whisper STT, Silero VAD, gTTS feedback. Three backend modes: Claude Desktop MCP, local llama.cpp, Whisper grammar. 55+ actions, 210+ phrase variants.

Mid 2025

MCP Integration

47 telescope tools exposed via Model Context Protocol. Claude Desktop can drive the telescope directly. Tool chaining: "goto + plate solve + autofocus + image" in one sentence.

Late 2025

3-Layer Tracking

Passive sidereal + active Kalman/EKF feedback + predictive ML noise tuning. Equatorial (4-state KF) and Alt-Az (6-state EKF) filters. Reported tracking error: under 2 arcseconds RMS.

Early 2026

Image Processing

GPU-accelerated stacking (ILGPU), star alignment (triangle matching + RANSAC), background extraction (RBF + polynomial), drizzle, narrowband, SPCC color calibration.

March 2026

v1.2.0 Release

First public release, with the feature set described above. Announced with a press kit and forum posts.

June 2026

v1.2.1/v1.2.2 PRO

Security audit in 9 commits. ML tracking layer activated. Kalman filter fixes. 131 tests passing.

The Technology

The application is built on three technology layers. The main application is C# targeting .NET Framework 4.8 with WPF for the UI: 200+ source files organized into a 7-project Visual Studio solution. The voice pipeline runs in Python 3.11 (bundled in the installer) because faster-whisper, Silero VAD, and gTTS are Python libraries without direct C# equivalents of similar performance. The MCP server runs on .NET 8, separate from the main application, and exposes 47 tools via the Model Context Protocol.

Engineering Milestones and Fixes

Audit Campaign Summary

9 commits across 4 subsystems

2 hardening areas — web auth, meridian flip

3 improvements — process lifecycle, session persistence, FITS handling

1 refinement — UI responsiveness, zenith rate

Several defects found in 2026 did not cause visible failures, because graceful degradation hid them. The Kalman filter's matrix dimension issue was caught by the tracking loop's exception handling, which kept the mount tracking but without the filter's corrections. The EKF computed its optimal rate, but the output path was not connected to the mount command layer. The ML layer's training pipeline trained only the RA axis and needed extension to dual-axis regression before the ML layer could engage.

All three issues shared a common pattern: the system continued to function, tests passed, and no exceptions surfaced to the user. The graceful degradation design, intended to keep the mount tracking during transient numerical issues, made the defects invisible in normal operation. They were found through systematic code review and mathematical validation.

Security Changes

The web authentication change was the main security fix. The AuthEnabled = false default was appropriate for local development, where typing a password for every API call during debugging adds unnecessary friction. With the change, authentication is activated automatically when the ngrok tunnel is started for remote access, so remote access is not left unauthenticated.

The meridian flip change added verification steps for physical safety. The scheduler now verifies that the pier side changed and halts the session if verification fails. This matters for unattended operation, where no one is present to stop the mount.

Where Voice Control Helps

In use so far, voice control has been most useful in three scenarios. First, the most common sequence: goto + plate solve + start imaging, given as one command, after which the observer can leave the scope to run. Second, cold-weather operation: changing exposure, filter, or target mid-sequence without touching the laptop. Third, accessibility: observers with mobility limitations, or those doing public outreach with groups around a scope, get a more natural way to interact.

Voice is less suited for precise numerical input, complex filter trees, and noisy environments. It does not replace click-based interaction; it complements it in the cases where hands-free operation is more practical.

Lessons Learned

Release, Then Review

v1.2.0 was released with working functionality. The later audit found defects that only a deliberate review would uncover.

Defaults Are Security Decisions

AuthEnabled = false was a development convenience. The change made secure-by-default the rule for authentication settings.

Physical Safety Requires Verification

Hardware commands must verify their effect. "The flip probably worked" is not acceptable when the alternative is equipment damage.

Keep a Development Log

The development trace log was used extensively during the audit. A structured review process was useful at this codebase size (200+ files).

What's Next

The roadmap includes comment-mode surgical edits (click on any part of a generated artifact and ask for changes), a skill marketplace (od skills install), one-command initialization (npx od init), and a packaged Electron build with bundled sidecars. The project is MIT-licensed and open to contribution.
