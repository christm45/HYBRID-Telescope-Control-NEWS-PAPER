Tracking layers

Passive sidereal tracking, active Kalman/EKF correction from plate solves, and ML-based tuning of the filter's noise parameters.

Many settings in a telescope control session are changed by hand at the computer: exposure time, target, filter, focus. At low temperatures, with gloves on and dew forming on the optics, each of these changes takes time and interrupts the session, and conditions such as seeing can change in the meantime. Reducing these manual interventions is one of the design goals of HYBRID Telescope Control.

A second goal is to accept complete instructions in natural language. A wake-word assistant can map a phrase such as "go to M31" to a single command. HYBRID is designed to handle a multi-step request such as "slew to M31, plate solve, center it, autofocus, and start imaging for two hours with 180-second exposures": it runs the steps in order, handles errors, and adapts to conditions with limited human intervention.

HYBRID is not intended as a replacement for established applications such as NINA, SGP or APT, which are mature and widely used. Its design goal is a self-guiding observatory: a system that tracks its own state, predicts its tracking errors and corrects them during the session. Design goals

Reactive and Predictive Control

Most telescope control follows a command-and-response model. The user, or a sequence the user has written, tells the mount where to point and the camera when to expose. Drift and focus shifts are detected by measurement — autoguiding, periodic autofocus — and corrected after they occur. Established sequencers automate much of this. For long-exposure astrophotography, where a single exposure can last 10 minutes and a session 8 hours, the approach works, but each correction follows the error it responds to.

Consider tracking accuracy. A telescope mount, even a good equatorial mount, drifts. Periodic error from the worm gear, flexure from temperature changes, atmospheric refraction, wind loading and polar alignment error all contribute to drift that degrades image quality. The standard solution is autoguiding: a second camera watches a guide star and sends correction pulses to the mount. This works well. In its basic form it is reactive — the guide star must drift before a correction is applied — although some guiding algorithms add prediction of periodic error.

HYBRID adds predictive tracking. The Kalman filter, a standard estimation method in navigation and control, estimates the mount's drift state from plate-solve measurements and projects it forward in time. Each correction therefore includes the drift expected before the next measurement, not only the error already observed.

Traditional Autoguiding (Reactive)

Guide star drifts → Camera detects error → Software computes correction → Pulse sent to mount → Mount corrects. Latency: 1-3 seconds. Error accumulates between corrections.

HYBRID Predictive Tracking

Plate solve measures position → Kalman filter predicts drift → ML layer adapts noise parameters → Correction includes predicted drift → Mount follows the target. Measurement cycle: about 5 seconds. Accuracy depends on how well the model predicts the drift.

The Three-Layer Architecture

The design assumes that no single tracking algorithm covers all conditions. Atmospheric conditions change, mechanical properties shift with temperature, and different mount geometries require different mathematical models. HYBRID therefore uses a three-layer architecture that combines passive, active and predictive tracking:

LAYER 1 — PASSIVE Sidereal tracking (firmware-level, always on) │ The mount's motors compensate for Earth's rotation at the native sidereal rate. │ No external software needed. This is the baseline. ▼ LAYER 2 — ACTIVE Kalman/EKF feedback (plate-solve every ~5 seconds) │ A plate-solve captures the actual RA/Dec position. The Kalman filter │ computes the error between predicted and actual position. A correction │ rate is applied as a MoveAxis delta on top of sidereal tracking. │ EQUATORIAL: 4-state linear KF (RA pos, RA vel, Dec pos, Dec vel) │ ALT-AZ: 6-state EKF (nonlinear coordinate transform, Jacobian) ▼ LAYER 3 — PREDICTIVE ML-enhanced noise tuning (learns over time) The machine learning layer observes the Kalman filter's prediction errors, trains a regression model on 24 features (position, time, weather, stats), and dynamically adjusts the filter's noise covariance matrices. When the model detects wind gusts → inflates process noise → trusts measurements more When observations are noisy → inflates measurement noise → trusts prediction more

The architecture was revised during field testing. The Kalman filter's matrix dimensions were corrected, the EKF correction pathway was completed, and the ML training pipeline was extended from single-axis to dual-axis regression. Each change followed a specific failure or limitation found in testing.

ASCOM: The Bridge to Hardware

Hardware Compatibility

  • ASCOM Alpaca — Network-based telescope control (REST API)
  • LX200 Serial — Legacy protocol for OnStep and similar controllers
  • Canon EDSDK — Direct live view via P/Invoke
  • UVC — USB webcam support for guide cameras
  • OnStep — Integration with OnStep controllers

HYBRID does not implement its own hardware protocols. It builds on the ASCOM Platform, the widely used standard for amateur telescope control on Windows. ASCOM provides a unified API for mount control, camera operations, focuser positioning, filter wheel selection and observatory automation. HYBRID's ASCOM controller wrapper (1,080 lines of C#) handles GOTO, slew, park, tracking and pulse-guide operations, including error handling and state management.

ASCOM defines how software talks to hardware; it does not define how an AI assistant discovers and calls telescope functions. For that, HYBRID uses the Model Context Protocol (MCP). It exposes 47 telescope tools through an MCP server, making them available to any MCP-compatible AI assistant. Claude Desktop can discover these tools, read their parameters, and chain them into multi-step sequences. The AI assistant handles the orchestration, and ASCOM handles the hardware.

YOU (voice or text) │ ▼ AI ASSISTANT (Claude Desktop / Local LLM / Whisper Grammar) │ "Slew to M31, plate solve, autofocus, image 30 min" │ ▼ MCP SERVER (.NET 8, 47 tools) │ goto_target → plate_solve → autofocus → start_imaging │ ▼ ASCOM API (Alpaca REST / LX200 Serial) │ ▼ HARDWARE (Mount + Camera + Focuser + Filter Wheel)

Use Cases for Voice Control

Voice control is intended to reduce manual interaction during the observing workflow. Typical scenarios:

Cold-weather operation. At -5°C, removing gloves to operate a laptop is uncomfortable and slows work down. Voice control allows changing targets, adjusting exposures and starting imaging sequences without using the keyboard.

Multi-tasking. While the telescope is imaging one target, you can queue the next target by voice, check the weather forecast, or adjust the scheduler — without interrupting the current imaging session.

Accessibility. Voice input offers an alternative to mouse and keyboard for observers with limited mobility. At public outreach events, it allows telescope control to be demonstrated by speaking.

Multi-step sequences. Commands can be chained. "Slew to M81, plate solve, autofocus, and start imaging for 30 minutes with 180-second exposures" is a single utterance that triggers four MCP tool calls, each dispatched to the ASCOM API. The AI assistant handles the sequence logic; the hardware handles the motion.

Push-to-talk is more reliable than wake-word detection near cooling fans and in wind. A false wake-word trigger could move the mount unexpectedly, so voice input is started by the user rather than always listening. Design decision log

The Self-Guiding Observatory

The longer-term design goal is autonomous operation: an observatory that carries out the following functions without manual input:

Estimate

The Kalman filter predicts mount drift. The ML layer adapts to changing conditions. The scheduler selects targets based on altitude, weather and session history. Decisions within a session are based on the system's own state estimates rather than manual input.

Act

ASCOM commands translate predictions into motion. The mount slews to targets. The camera captures exposures. The focuser maintains focus as the temperature drops. The filter wheel selects the filter for each target. The meridian flip is executed and then verified.

Adapt

When clouds arrive, the scheduler pauses and waits. When the seeing improves, the ML layer tightens the noise parameters. When a target sets below the horizon limit, the system moves to the next target. When the session ends, the telescope parks and the system shuts down.

Each of these components is implemented in the current version: the Kalman filter, the ML layer, the scheduler, the voice pipeline and the ASCOM interface. The remaining work is integration — making them operate together reliably in real observatory conditions, with falling temperatures, passing clouds, and equipment running unattended through the night.

A Note on Open Source

HYBRID Telescope Control is MIT-licensed and open to contribution. The source code is available for inspection, modification and redistribution. Open source lets users read the code that makes decisions for unattended equipment, such as a mount running through the night.

The design draws on more than 20 open-source projects: NINA's sequencer architecture, PHD2's guiding algorithms, Stellarium's sky chart rendering, Siril's image stacking, the OnStep community's hardware interface standards, and the MCP ecosystem's tool protocol. HYBRID is released under the MIT license so that its own code is available to others in the same way.

The codebase comprises more than 200 source files. After the security audit, current work focuses on integration and on the planned roadmap items: multi-star tracking, adaptive process noise, acceleration states, online learning and cross-mount transfer learning. Project documentation
