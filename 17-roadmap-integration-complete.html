Closing the Roadmap: Six Phases From Acceleration States to Security Hardening

Twenty items taken from this site's public roadmap pages, closed in one sequenced integration pass — new Kalman/EKF state terms, anisotropic ML noise tuning, per-mount transfer learning, an adaptive fusion gain, ASCOM-layer latency work, and a fix for credentials stored in plaintext. Phase 0: Testing the Existing Math First

Before touching a single line of the production Kalman or Extended Kalman filter…

None of this changed behavior. The purpose was to have regression tests in place before later changes, so that any breakage they caused would be detected. Twenty-three tests were added in this phase, all of them regression guards for phases that had not been written yet.

Phase 1: Acceleration States and Multi-Star Fusion

The 4-state linear Kalman filter (equatorial mounts) and the 6-state Extended Kalman filter (Alt-Az mounts) both gained acceleration terms — a second derivative that a constant-velocity model cannot represent. With it, the filters can model periodic-error harmonics and wind-induced disturbance rather than only react to them. In the EKF, the new acceleration terms drive the bias rate inside the nonlinear state transition, extending by one derivative the observability technique the filter already used to make bias estimable.

Multi-star tracking was added as a pre-filter fusion step rather than a joint multi-measurement rewrite of the update equations: several simultaneous guide-star observations are combined — MAD-based outlier rejection, then weighted averaging — into the single (RA error, Dec error) pair the filter already knows how to consume. This was a deliberate trade-off against a mathematically purer joint update, made to keep the filters' shared core math, used by every existing single-star call site, unchanged. It has no live caller yet: the plate-solve pipeline produces one solved position per cycle today, not per-star centroids, so this fusion primitive is waiting for a future multi-centroid measurement source.

The main difficulty in this phase was backward compatibility, not the math. GetStateVector() and GetCovarianceMatrix() keep returning their original 4-wide shape on both filters, because the web API and two UI diagnostic panels read them by raw array position, not only through the dimension-agnostic tuple accessors. Widening those two methods would have silently broken a documented API schema. Full-width data now lives behind new GetNativeStateVector()/GetNativeCovarianceMatrix() methods instead.

Phase 3: ML Pipeline Upgrades

Feature expansion: cloud cover is now fully wired from weather data the pipeline already fetches. Focuser temperature and mount current draw were added as opt-in callbacks with safe defaults, since no standard ASCOM Alpaca telescope property exposes current draw; this is a limitation of the protocol, not an omission.

Model versioning with automatic rollback.

Cross-mount transfer learning.

“Online learning” was implemented as an approximation: ML.NET's SDCA trainer has no incremental-fit API, so periodic full retrains continue. What Phase 3 added is a rolling self-prediction memory — each training sample now carries what the model predicted just before that observation — which gives the retrained model temporal continuity across sessions. It is documented as an approximation, not as true online learning.

Phase 4: Adaptive Fusion Gain

Multi-target feature sharing indexes training history by declination band.

Adaptive gain scheduling replaced a fixed 70/30 Kalman/ML blend — used at all four fusion call sites in the tracking controller — with a weight computed from ML confidence, current wind speed, and recent tracking-error stability. Worse seeing conditions shift the blend toward the ML layer, which takes weather data as input, unlike the Kalman model; a volatile recent error history shifts it back toward the more conservative filter output.

An explainability layer surfaces ML.NET's permutation feature importance so that a future panel could show which features drive a given drift prediction. One caveat: it compiles against the installed ML.NET package (an initial assumption about the API shape was wrong and the compiler caught it), but it has not yet been run against a live trained model; that needs a real training session to verify end to end.

Phase 5: ASCOM Communication Over HTTP

ASCOM Alpaca is a REST protocol, not WebSocket, so the roadmap's “WebSocket bridge” item was reinterpreted as HTTP keep-alive tuning. This revealed a specific issue: .NET Framework defaults to 2 connections per host, which would have serialized the new concurrent RA/Dec dispatch as soon as anything else shared that host. The limit was raised to 10. The RA-axis and Dec-axis motor corrections are now sent concurrently rather than sequentially; this is also what “multi-command batching” came to mean, since Alpaca's REST design cannot combine two endpoints into one transaction.

A rate-smoothing filter and a predictive sync-timing scheduler were both added as small, pure, standalone functions rather than logic inside the tracking loop, so that the math can be unit-tested without a real mount or a real socket.

Phase 6: Credential Encryption and Audit Logging

The security phase included a finding from the initial research pass, made before work on the six phases began: webserver_config.json stored the web server's username, password, and MCP API key in plaintext, including the unchanged factory-default password. DPAPI-based encryption now protects that file at rest, and an existing plaintext file is migrated to the encrypted format the next time it is saved.

Audit logging reused the project's existing structured logger.

A further finding concerned the CI workflow rather than the security code: the GitHub Actions pipeline only ran one test project. The tests from every phase of this integration — all 259 of them, the entire Kalman/EKF math suite, the ML pipeline tests, the ASCOM and security tests — were in a project that CI did not run. Adding one workflow step fixed this.

What Was Deferred

Not everything was wired all the way through, and the gaps are documented. Focuser-temperature, mount-current-draw, and mount-identity callbacks exist as working infrastructure with safe defaults, but connecting them to a live source requires a larger constructor and threading change to the tracking controller that did not belong in this pass. The explainability layer's permutation-importance output has not been checked against a real trained model. A post-flip mount re-sync still runs outside the new predictive sync scheduler, because the class that triggers it does not hold a reference to the tracking controller today.

The same approach applied in every phase: implement the feature, connect it to live code where that is low-risk, and document what is deferred and why, rather than forcing a larger change into the pass or dropping the item.

Lessons Learned

A Flaky Test Is Still a Bug

One isolation test in the EKF suite asserted exact equality between two separately constructed filter instances. The EKF reads the system clock internally for sidereal time, so two instances built microseconds apart can diverge by a small but non-zero, timing-driven amount. The test failed once and passed on immediate rerun, which is typical of a flaky test. The fix was a tolerance loosened by nine orders of magnitude, with a comment explaining why, so that the tolerance is understood as intentional.

The Pipeline Is Part of the Test Suite

A test suite that CI does not run provides no protection, even when the CI check shows green for another project. Finding and closing that gap was one of the more significant results of this pass.

Sequencing Over Speed

Seven phases (zero through six), each one gated on a clean build-and-test pass before the next started, each documented in its own specification addendum. Changing everything at once would have been faster, but it would have made it much harder to attribute a failure to a specific change.
