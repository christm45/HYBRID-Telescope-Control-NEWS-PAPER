Security and Crash Fixes: 15 Critical and High-Severity Issues Across 12 Files

A five-agent audit of the codebase produced 135 findings. This pass fixed 15 CRITICAL and HIGH-severity issues — hardcoded secrets, division-by-zero crashes, UI deadlocks, memory leaks, and incorrect build paths.
By Bogdan • July 7, 2026 • PHASE 7 AUDIT • v1.3.0 PRO

Audit in Numbers

135
Findings from 5 parallel audit agents

16 CRITICAL, 39 HIGH, 36 MEDIUM, 25 LOW. 15 CRITICAL and HIGH fixes applied in this pass; the remaining items are recorded in the fix log.

Some defects produce no error messages or stack traces in normal use. Examples from this audit: a signing key stored in an XML file, a division that works at mid latitudes but fails at the poles, and a synchronous wait that deadlocks only under particular timing. Code of this kind can pass the existing tests because the tests do not exercise the edge case.

After the first audit (Fixes 1–18, July 2026), a second audit ran five parallel agents — one for C# GUI, one for C++ native code, one for Python STT services, one for build and configuration, and one for the MCP server and tests. They reported 135 new findings. Sixteen were CRITICAL. Thirty-nine were HIGH. The rest were lower-priority items. This article describes the 15 CRITICAL and HIGH fixes applied in this pass, and the conditions under which each defect appeared.

Fix 21: The Hardcoded Signing Key

The HMAC signing key used to validate license keys was sitting in App.config in plaintext: HYBRID_TELESCOPE_CONTROL_2026_SECRET_KEY_V1. Anyone with a copy of the source code — or a decompiled binary — could generate valid license keys for any machine. The LicenseManager.cs file had a fallback constant that returned this key when no environment variable was set, which was always.

We removed the hardcoded value from both the config file and the C# constant. GetHmacKey() now throws InvalidOperationException if neither the HYBRID_LICENSE_HMAC_KEY environment variable nor the App.config entry is present. This is a breaking change for any installation that relied on the default; that is intentional.

A default signing key would be the same key in every installation. With the fallback removed, a key must be configured before licence validation runs. Fix 21, Security Audit

Fix 25: Division by Zero at the Poles

The AltAzToRaDec function in MathUtils.cpp divides by cos(dec) when computing hour angle. At the celestial poles, declination reaches plus or minus 90 degrees, and cos(90°) is zero. The resulting NaN propagates through the coordinate pipeline into telescope motor commands, causing erratic pointing near the poles — a case the tests, which all ran at latitude 45°N, did not cover.

The fix: an epsilon guard. If the absolute value of cos(dec) is below 10−10, the hour angle defaults to zero (the local sidereal time). The Haversine distance function had a similar issue: its intermediate variable a could exceed 1.0 due to floating-point imprecision, making sqrt(1-a) a square root of a negative number. We clamped a to [0, 1] before the square root.

Fix 27: The WPF Deadlock Pattern

Six call sites in MainWindow.Imaging.cs were using .GetAwaiter().GetResult() to synchronously wait for async ASCOM HTTP calls. On the WPF UI thread, this can deadlock: the async continuation tries to post back to the SynchronizationContext, which is blocked by the synchronous wait. The deadlock would manifest only under specific timing conditions — when the ASCOM response arrived while the UI thread was still processing — which makes it difficult to reproduce in testing.

We wrapped all six call sites in Task.Run(() => ...), which moves the async work to the thread pool and prevents the SynchronizationContext capture. This is the standard WPF pattern for breaking sync-over-async deadlocks.

Fix 28: The Dispose Deadlock

ASCOMControllerWrapper.Dispose() called DisconnectAsync().Wait(2 seconds). If Dispose was called from the UI thread (which it is, during window shutdown), the same SynchronizationContext deadlock would occur. The fix: wrap in Task.Run() so the async disconnect runs on the thread pool while Dispose returns immediately.

Fix 29: The MemoryStream Leak

The MCP SSE proxy in WebServer.cs created a MemoryStream for each incoming request body but never disposed it. Over hours of continuous operation, the undisposed streams accumulated. The fix was one line: using (var bodyStream = new MemoryStream()). The using block ensures disposal even if the method throws.

Fix 30: The 24-Hour Timeout

The shared HttpClient for MCP proxy requests had a 24-hour timeout. A hung connection would block a thread pool slot for an entire day. It is now 5 minutes, which is long enough for SSE streams and short enough to avoid holding thread-pool slots indefinitely.

The Build and Configuration Fixes

Six HIGH-severity issues were in build configuration rather than runtime code:

  • Fix 22 (.gitignore): EXTRA PROGRAMS/ and GENERATE LICENCE KEYS/ were at root level in .gitignore but the actual directories were under extras/. The license key generator and 400+ MB of installer executables were tracked in git.
  • Fix 23 (Deploy scripts): Server IP 192.168.1.55 and SSH username christm45 were hardcoded in deploy-all.bat. Replaced with environment variables HYBRID_VM_IP and HYBRID_VM_USER.
  • Fix 24 (.vscode/mcp.json): All paths were hardcoded to C:\Users\Bogdan\Desktop\release\.... Replaced with ${workspaceFolder} variables.
  • Fix 33 (.csproj): The TelescopeMCP Exists() condition checked ..\TelescopeMCP\dist\ while the Include used ..\tools\TelescopeMCP\dist\. The condition always failed, so the MCP server was never copied to build output.
  • Fix 34 (NSIS): The installer referenced download_whisper_mic.py but the actual file is download_whisper_model.py.
  • Fix 35 (OxyPlot): ImageProcessing referenced OxyPlot.Wpf 2.1.2 while GUI referenced 2.2.0, risking TypeLoadException at runtime.

Fixes 31 and 32: Data Integrity

SimpleJSON.h’s value parser used find('"') to locate the closing quote of a JSON value. If the value contained an escaped quote (\"), the parser would match the backslash-escaped quote and truncate the value. We replaced the plain find() with a loop that skips escape sequences.

ConfigManager.cpp’s WriteFile() did not check whether the write actually succeeded. On disk-full or I/O error, it returned true, and the caller assumed the config was saved. Next load would read stale or empty data. We added file.flush() plus a file.fail() check.

Build Verification

After all 15 fixes were applied, we ran a clean rebuild of the entire solution. All 12 projects compiled with zero errors. The output binary HYBRID_Telescope_Control.exe is 9.2 MB. Each change was also reviewed by re-reading the modified code.

What Changed

15 CRITICAL and HIGH fixes across 12 files. Security, crashes, deadlocks, memory leaks, data corruption, and build configuration.

What Didn’t Change

The existing test suites pass, including the 1,495 tests from Phase 5 (of which 1,066 are Python tests). No regressions were observed.

What Remains

The audit reported 135 issues. This pass applied 15 fixes to CRITICAL and HIGH-severity findings. The 61 MEDIUM and LOW items are documented in the fix log. They include empty catch blocks that swallow errors, data races in non-critical paths, async methods without await, date-dependent test cases, and various cosmetic issues. They will be addressed when those files are next changed.

The scope of this pass was limited to issues that could cause crashes, deadlocks, resource leaks or security exposure. Lower-severity items were deferred.
