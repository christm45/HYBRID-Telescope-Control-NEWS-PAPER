Imaging Pipeline

Stacking a Whole Night: 26 GB Refused, 1 GB Delivered

A 564-frame session asked for 26 GB of RAM and was turned away. Rebuilding the stacker to read horizontal bands off the disk brought that to about 1 GB — with a master identical to the old one, pixel for pixel. Along the way we found that the application’s own default settings quietly bypassed every bit of it, and that drizzle had been shipping switched off for years because nobody ever handed it the dither offsets.
By Bogdan • August 14, 2026 • DEV LOG • v1.3.7 PRO

One Real Session

13:34
563 of 564 frames stacked, calibrated and normalized

4144×2822 each, on a machine that previously refused the job outright. Peak working set: roughly 780 MB. The frame that did not make it was cut in half by an interrupted capture, and is excluded on purpose.

The bug report was one sentence: loading 500 frames and pressing STACK gives “Stacking cancelled — not enough memory, 43 GB needed.”

The memory guard was right. Every frame was being held as a float[] for the entire duration of the run. Five hundred frames of 4144×2822 is 21.8 GB before anything else happens, and alignment doubles it while it builds the warped copy. The guard was doing its job. The pipeline behind it was the problem.

Nothing about combining images requires all of them at once. Stacking is a per-pixel operation: to produce row 900 of the master you need row 900 of every frame, and nothing else. That observation is the whole article.

Bands, and the Discipline of Being Identical

The stacker now walks the image in horizontal bands, seeking each frame’s rows straight off the disk and combining them with the same per-pixel code the old path used. A 500-frame session holds about 1 GB regardless of frame count, against 21.8 GB resident before.

The rule we set for ourselves was that this must not be a second answer. If reading from disk produced a subtly different master, the result would depend on how much RAM happened to be free — the worst kind of non-determinism, because it would never reproduce on the machine you debug it on. So the tests assert equality with zero tolerance, band by band, against the whole-frame result.

That discipline caught things immediately. The decode path had to reproduce the whole-frame conversion exactly, including a (ushort) truncation that happens before dividing by 65535. Rounding instead — which is arguably more correct — puts the two paths one ADU apart, and the master would then depend on which code path ran. We kept the truncation and documented why.

Reading from disk is a memory strategy, not a different answer. The moment it becomes a different answer, it is a bug that only appears on other people’s computers. On the zero-tolerance rule

Alignment Splits in Two

Alignment was the last thing forcing a whole session into memory, and it was the expensive one: it held every frame and built a warped copy beside it. That is where the 43 GB came from.

But alignment is two different jobs wearing one coat. Measuring a frame’s transform — detect stars, match the pattern, fit the affine — genuinely needs a whole frame, but only one at a time. Applying that transform is per-band work: an output band is read from a source band, shifted and slanted by the transform, plus the reach of the resampling kernel.

So it is split. Transforms are measured one frame at a time, costing one frame of memory. The warping happens inside the band loop, reading exactly the rows that band needs.

Rotation is the part that punishes naive implementations. A shifted band is still a band. A rotated band is a slanted swathe whose height grows with the image width, not the band height. On a 4144-pixel-wide sensor, a fifth of a degree of field rotation adds a dozen rows to every read. That relationship also made writing an honest regression test harder than writing the fix — more on that below.

The Findings That Only Running It Revealed

Here is the uncomfortable part. All of the above was implemented, tested, and green — and none of it ran.

We launched the actual application, loaded the actual 564-frame session, and pressed STACK. It said “Stacking cancelled — not enough memory.” Again.

The application ships with three settings that each, independently, sent the session back to the old path:

GPU acceleration, ticked

On by default above ten frames. GPU stacking needs every frame resident and cannot read from disk at all, so a large session went straight back to being refused. It now yields: when a session does not fit but can be banded, banding is not a downgrade, it is the only route that finishes.

Equalize background, ticked

Normalization combined with alignment was refused by the banded path. It now measures its factors on the warped frames, at the cost of a second warp in the preliminary pass. Refusing meant the feature never engaged for a default session — the exact case it exists for.

The third was calibration. A master dark was loaded, as it would be for any real session, and calibration forced whole frames. Yet calibration is per pixel and the masters are single frames: a band of a light needs only the matching band of each master. It bands now, through one shared implementation used by both routes, because two copies of that arithmetic would make the master depend on which route the session took.

No test suite was ever going to find this. It required launching the executable and clicking the button.

One Bad Frame Refused the Whole Session

With the defaults fixed, the run got further: it measured all 563 transforms, took fifteen minutes doing it — and then declined, falling back to the in-memory path, which refused for memory.

The band buffers were sized by the worst transform in the session. RANSAC had returned one badly rotated frame; that single frame needed a slice most of the image tall, and multiplying its demand by 563 frames blew the 1.5 GB budget seventeen times over. One bad frame refused everyone.

Buffers are sized per frame now. The wild one costs 47 MB — one frame — and nobody else pays. Frames whose alignment demands an outsized slice are reported as a warning, because such a transform is suspect and worth looking at.

Writing the regression test for this took longer than the fix, and taught the more useful lesson. A rotated band’s extra reach scales with image width, so a narrow test fixture cannot tell per-frame sizing from worst-frame sizing — the rotated frame costs no more than the others and the bug hides. The band also has to be much shorter than the image, as it is in reality. We verified the test both ways: it passes with the fix and fails without it. A regression test that cannot fail is decoration.

A regression test that has never failed on the bug it was written for is not a test. It is a comment with a runtime cost. On writing the per-frame sizing test

Drizzle Was Never Wired Up

Drizzle has been in the codebase for years with its checkbox greyed out. The XAML comment beside it was refreshingly honest about why: StackViaDrizzle handed the drizzle engine null transforms, so every frame was dropped at the same place on the output grid. That produces an upscaled average wearing a reconstruction’s clothes — plausible-looking and wrong, which is worse than a visibly missing feature.

The missing piece was per-frame dither offsets. That is exactly what the new alignment measurement produces.

Drizzle now streams: a frame is dropped onto the output grid and never looked at again, so the natural streaming axis is frames rather than rows. The accumulators are sized by the output — about 750 MB at 2× on this sensor — and do not grow with frame count.

The test that matters compares against a known high-resolution truth: an undersampled synthetic scene, sixteen frames dithered by quarter pixels, drizzled 2×. It must beat the same frames stripped of their offsets — that is, it must beat the old behaviour. It does, by 50 percent RMS.

Writing that test also caught an error in the test itself before it caught anything in the engine. A frame that samples the scene at +dx must have its pixels placed back at +dx; we had the sign inverted, which doubles the error instead of removing it, and the “dithered” result came out worse than the blind one. The engine was right. The measurement was wrong. That is worth remembering the next time a benchmark says something surprising.

Testing: When the Machine Is the Variable

Three suites, run clean: 461 imaging tests, 638 GUI tests, 23 imaging-orchestration tests. All green.

Getting there meant confronting a different kind of flakiness. Two performance benchmarks failed reporting 1,251,245 ms and 1,252,556 ms against a 60-second ceiling. Those numbers are not slow code — they are almost exactly the duration of the entire test run. The assembly executes sixteen test methods in parallel, and those two were starved from their first line to their last while everything else, plus a Release build, had the cores.

A wall-clock ceiling cannot share a machine. Marking the benchmarks [DoNotParallelize] took the suite from 21 minutes with two failures to 3 minutes 10 with none. An earlier attempt to fix a similar test with “best of three” had made it worse — every repeat competed too.

Against Real Data, Not Fixtures

Every other test in this area builds its own FITS files, which means they all agree with each other about what a FITS file is. So we pointed the whole thing at the real capture: 564 frames of NGC 2903, 4144×2822 RGGB, 23 MB apiece, with the 100-frame master dark the observer actually uses.

Both paths produce an identical master, pixel for pixel — unaligned, and aligned with transforms measured from disk. 563 of 564 frames, in 13 minutes 34, at roughly 780 MB.

The 564th is excluded on purpose. It was cut to 44 percent of its size by an interrupted capture, and is dropped before the run starts with a warning — rather than failing the session partway down the image, which would have stacked the top of the master from more frames than the bottom.

Real data also found something fixtures never could: a band of a real frame is 4 MB, and the band reader allocated a fresh buffer for every read. That is 11,500 large-object-heap allocations over a full session, and the heap climbed to 1.7 GB on a ten-frame run — more than simply loading the frames would have cost, which defeats the entire point. It reads through a reused 64 KB buffer now, below the large-object threshold.

Two Corrections With No Excuse

Once stacking ran from disk, quality weighting and “auto-reject worst N percent” were silently ignored: Weight and FrameRejected are derived from the measured statistics rather than copied with them, and the new path never derived them. Every frame came out weighted equally and none was ever dropped.

Separately, “Images stacked” and the SNR estimate counted frames loaded rather than frames combined. A run that discarded the worst 25 percent still reported every frame as used, and overstated the SNR gain to match.

And a smaller one that users see first: an imported session showed every frame rated Poor, in red, before anything had analysed it. The rating was derived from the quality score alone, and an unanalysed frame scores zero. That is a verdict on data nobody has looked at. There is now a distinct “not analysed” state, shown as a dash in grey; a frame that was measured and came out bad still says Poor.

Shipping It

Packaging has its own traps, and this release walked into two.

The first: running dotnet build silently replaces the executable in the Release output using a toolchain that cannot compile the C++ projects. The result is an .exe from one toolchain sitting beside Core.dll and Shared.dll from another — and the packaging gate checks that those DLLs are present, not that they were built together. We caught it by timestamp: the executable was from 13:10 today, the native DLLs from 21:11 yesterday. The fix is to delete the intermediates and run the master build script, because MSBuild otherwise judges everything up to date and rebuilds nothing.

The second: editing a .bat file with a Unix tool converted its line endings from CRLF to LF, and cmd.exe then mis-parses if/else blocks. The build printed both [OK] HYBRID_Telescope_Control.exe and [ERROR] Executable missing for the same check, which is a memorable way to learn that both branches ran.

The installer is 2.62 GiB. Its SHA256 is recorded in version.json, and the deploy verifies the uploaded file against that value on the server before anything old is removed — a guard added after a previous release shipped a silently corrupted upload. We also confirmed the new archive is genuinely new rather than an old one appended to: 7z a updates an existing archive rather than replacing it, which is how a 1.3.4 payload once ended up inside a 1.3.5 installer.

What Remains

Local (per-tile) normalization still takes the whole-frame path. Comet stacking does not exist; DeepSkyStacker has had three modes of it for years. The MAD-based rejection variants and noise-weighted stacking that Siril offers are not implemented.

And one honest gap: the full end-to-end run — measure and stack, aligned, on all 564 frames in one pass through the interface — has not been completed since the last fix. The mechanism is covered by a regression test that fails without it, and the engine has done the work at scale. But the button has not been pressed all the way through, and this article is not going to pretend otherwise.

What Changed

Banded stacking with alignment, calibration and normalization. Drizzle working for the first time. Nine correctness fixes in the surrounding pipeline. 1,122 tests green across three suites.

What Didn’t

The master. Every banded result is verified bit-for-bit against the whole-frame path, on synthetic fixtures and on the real 564-frame session.

The session that could not be stacked at all now stacks in fourteen minutes on the same machine. That was the goal, and everything above is what it actually took — including the parts where the code was right and the test was wrong.
