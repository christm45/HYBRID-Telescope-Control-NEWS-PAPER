Imaging Pipeline

Disk-Banded Stacking: A 564-Frame Session in About 1 GB of RAM

A 564-frame session required 26 GB of RAM and was refused by the memory check. The stacker now reads horizontal bands from disk, which brings memory use to about 1 GB, and the resulting master is identical to the whole-frame result pixel for pixel. The work also found that three default settings routed sessions back to the old path, and that drizzle had been disabled for years because it was never given the dither offsets.
By Bogdan • August 14, 2026 • DEV LOG • v1.3.7 PRO

One Real Session

13:34
563 of 564 frames stacked, calibrated and normalized

4144×2822 each, on a machine that previously refused the job. Peak working set: roughly 780 MB. The frame that did not make it was cut in half by an interrupted capture, and is excluded on purpose.

The bug report was one sentence: loading 500 frames and pressing STACK gives “Stacking cancelled — not enough memory, 43 GB needed.”

The memory guard was right. Every frame was being held as a float[] for the entire duration of the run. Five hundred frames of 4144×2822 is 21.8 GB before anything else happens, and alignment doubles it while it builds the warped copy. The guard was doing its job. The pipeline behind it was the problem.

Nothing about combining images requires all of them at once. Stacking is a per-pixel operation: to produce row 900 of the master you need row 900 of every frame, and nothing else. The new stacker is built on that property.

Banded Stacking and Bit-Identical Output

The stacker now walks the image in horizontal bands, seeking each frame’s rows straight off the disk and combining them with the same per-pixel code the old path used. A 500-frame session holds about 1 GB regardless of frame count, against 21.8 GB resident before.

The design requirement was that the banded path must produce the same result as the whole-frame path. If reading from disk produced a slightly different master, the result would depend on how much RAM was free — a form of non-determinism that is hard to reproduce on a different machine. So the tests assert equality with zero tolerance, band by band, against the whole-frame result.

The zero-tolerance tests found a difference early. The decode path had to reproduce the whole-frame conversion exactly, including a (ushort) truncation that happens before dividing by 65535. Rounding instead — which is arguably more correct — puts the two paths one ADU apart, and the master would then depend on which code path ran. We kept the truncation and documented why.

Reading from disk changes memory use, not the result. If the two paths disagreed, the master would depend on the amount of free RAM. On the zero-tolerance rule

Alignment Splits in Two

Alignment was the last thing forcing a whole session into memory, and it was the expensive one: it held every frame and built a warped copy beside it. That is where the 43 GB came from.

Alignment, however, consists of two separate steps. Measuring a frame’s transform — detect stars, match the pattern, fit the affine — genuinely needs a whole frame, but only one at a time. Applying that transform is per-band work: an output band is read from a source band, shifted and slanted by the transform, plus the reach of the resampling kernel.

So it is split. Transforms are measured one frame at a time, costing one frame of memory. The warping happens inside the band loop, reading exactly the rows that band needs.

Rotation needs particular care. A shifted band is still a band. A rotated band is a slanted swathe whose height grows with the image width, not the band height. On a 4144-pixel-wide sensor, a fifth of a degree of field rotation adds a dozen rows to every read. That relationship also made it harder to write a regression test that detects the problem than to write the fix — see below.

Issues Found by Running the Application

All of the above was implemented and its tests passed, but with the default settings the new path was not used.

Launching the application, loading the 564-frame session and pressing STACK produced the same message: “Stacking cancelled — not enough memory.”

The application ships with three settings that each, independently, sent the session back to the old path:

GPU acceleration, ticked

On by default above ten frames. GPU stacking needs every frame resident and cannot read from disk at all, so a large session went straight back to being refused. It now yields: when a session does not fit in memory but can be banded, the banded path is used, since it is the route that can complete.

Equalize background, ticked

Normalization combined with alignment was refused by the banded path. It now measures its factors on the warped frames, at the cost of a second warp in the preliminary pass. Previously the refusal meant the banded path was never used for a default session, which is the case it was designed for.

The third was calibration. A master dark was loaded, as it would be for any real session, and calibration forced whole frames. Yet calibration is per pixel and the masters are single frames: a band of a light needs only the matching band of each master. It bands now, through one shared implementation used by both routes, because two copies of that arithmetic would make the master depend on which route the session took.

The unit tests did not cover the application’s default settings; this was found by launching the executable and running a stack.

One Bad Frame Refused the Whole Session

With the defaults fixed, the run got further: it measured all 563 transforms, took fifteen minutes doing it — and then declined, falling back to the in-memory path, which refused for memory.

The band buffers were sized by the worst transform in the session. RANSAC had returned one badly rotated frame; that single frame needed a slice most of the image tall, and multiplying its demand by 563 frames exceeded the 1.5 GB budget by a factor of seventeen. A single outlier frame caused the whole session to be refused.

Buffers are sized per frame now. The outlier costs 47 MB — one frame — and the other frames are unaffected. Frames whose alignment demands an outsized slice are reported as a warning, because such a transform is suspect and worth looking at.

Writing the regression test for this took longer than the fix. A rotated band’s extra reach scales with image width, so a narrow test fixture cannot tell per-frame sizing from worst-frame sizing — the rotated frame costs no more than the others and the bug hides. The band also has to be much shorter than the image, as it is in reality. The test was checked in both directions: it passes with the fix and fails without it.

The per-frame sizing test was run against the old code to confirm that it fails there, and against the fix to confirm that it passes. On writing the per-frame sizing test

Drizzle Was Never Wired Up

Drizzle has been in the codebase for years with its checkbox greyed out. The XAML comment beside it stated the reason: StackViaDrizzle handed the drizzle engine null transforms, so every frame was dropped at the same place on the output grid. That produces an upscaled average rather than a drizzle reconstruction, which is why the option was left disabled.

The missing piece was per-frame dither offsets. That is exactly what the new alignment measurement produces.

Drizzle now streams: a frame is dropped onto the output grid and never looked at again, so the natural streaming axis is frames rather than rows. The accumulators are sized by the output — about 750 MB at 2× on this sensor — and do not grow with frame count.

The test that matters compares against a known high-resolution truth: an undersampled synthetic scene, sixteen frames dithered by quarter pixels, drizzled 2×. The result must be closer to the truth than the same frames stripped of their offsets, which is the old behaviour. On this test its RMS error is 50 percent lower.

Writing that test also caught an error in the test itself before it caught anything in the engine. A frame that samples the scene at +dx must have its pixels placed back at +dx; we had the sign inverted, which doubles the error instead of removing it, and the “dithered” result came out worse than the blind one. The engine was correct; the error was in the test’s measurement.

Testing and Parallel Benchmark Timing

Three suites were run: 461 imaging tests, 638 GUI tests, 23 imaging-orchestration tests. All pass.

Getting there required fixing a timing-related failure. Two performance benchmarks failed reporting 1,251,245 ms and 1,252,556 ms against a 60-second ceiling. Those numbers are not slow code — they are almost exactly the duration of the entire test run. The assembly executes sixteen test methods in parallel, and those two were starved of CPU for their whole duration while the other tests and a Release build ran.

A wall-clock limit is unreliable when tests share the machine. Marking the benchmarks [DoNotParallelize] took the suite from 21 minutes with two failures to 3 minutes 10 with none. An earlier attempt to fix a similar test with “best of three” had made it worse — every repeat competed too.

Against Real Data, Not Fixtures

Every other test in this area builds its own FITS files, so they share the same assumptions about what a FITS file contains. The pipeline was therefore also run against a real capture: 564 frames of NGC 2903, 4144×2822 RGGB, 23 MB apiece, with the 100-frame master dark the observer actually uses.

Both paths produce an identical master, pixel for pixel — unaligned, and aligned with transforms measured from disk. 563 of 564 frames, in 13 minutes 34, at roughly 780 MB.

The 564th is excluded on purpose. It was cut to 44 percent of its size by an interrupted capture, and is dropped before the run starts with a warning — rather than failing the session partway down the image, which would have stacked the top of the master from more frames than the bottom.

Real data also found something fixtures never could: a band of a real frame is 4 MB, and the band reader allocated a fresh buffer for every read. That is 11,500 large-object-heap allocations over a full session, and the heap climbed to 1.7 GB on a ten-frame run — more than simply loading the frames would have cost, which negated the memory saving. It reads through a reused 64 KB buffer now, below the large-object threshold.

Corrections to Weighting, Rejection and Reporting

Once stacking ran from disk, quality weighting and “auto-reject worst N percent” were silently ignored: Weight and FrameRejected are derived from the measured statistics rather than copied with them, and the new path never derived them. Every frame came out weighted equally and none was ever dropped.

Separately, “Images stacked” and the SNR estimate counted frames loaded rather than frames combined. A run that discarded the worst 25 percent still reported every frame as used, and overstated the SNR gain to match.

And a smaller one that users see first: an imported session showed every frame rated Poor, in red, before anything had analysed it. The rating was derived from the quality score alone, and an unanalysed frame scores zero. That rating was misleading for frames that had not been measured. There is now a distinct “not analysed” state, shown as a dash in grey; a frame that was measured and came out bad still says Poor.

Shipping It

Two packaging problems affected this release.

The first: running dotnet build silently replaces the executable in the Release output using a toolchain that cannot compile the C++ projects. The result is an .exe from one toolchain sitting beside Core.dll and Shared.dll from another — and the packaging gate checks that those DLLs are present, not that they were built together. We caught it by timestamp: the executable was from 13:10 today, the native DLLs from 21:11 yesterday. The fix is to delete the intermediates and run the master build script, because MSBuild otherwise judges everything up to date and rebuilds nothing.

The second: editing a .bat file with a Unix tool converted its line endings from CRLF to LF, and cmd.exe then mis-parses if/else blocks. The build printed both [OK] HYBRID_Telescope_Control.exe and [ERROR] Executable missing for the same check, showing that both branches had executed.

The installer is 2.62 GiB. Its SHA256 is recorded in version.json, and the deploy verifies the uploaded file against that value on the server before anything old is removed — a guard added after a previous release shipped a silently corrupted upload. We also confirmed that the new archive was created fresh rather than appended to an old one: 7z a updates an existing archive rather than replacing it, which is how a 1.3.4 payload once ended up inside a 1.3.5 installer.

What Remains

Local (per-tile) normalization still takes the whole-frame path. Comet stacking is not implemented (DeepSkyStacker, for comparison, offers three comet modes). MAD-based rejection variants and noise-weighted stacking, both available in Siril, are not implemented.

One gap remains: the full end-to-end run — measure and stack, aligned, on all 564 frames in one pass through the interface — has not been completed since the last fix. The mechanism is covered by a regression test that fails without it, and the engine has done the work at scale. A complete run through the interface is still to be done.

What Changed

Banded stacking with alignment, calibration and normalization. Drizzle enabled, using measured dither offsets. Nine correctness fixes in the surrounding pipeline. 1,122 tests passing across three suites.

What Didn’t

The master. Every banded result is verified bit-for-bit against the whole-frame path, on synthetic fixtures and on the real 564-frame session.

The session that previously could not be stacked now stacks in about fourteen minutes on the same machine. The sections above describe the changes required, including one case where the code was correct and the test was wrong.
