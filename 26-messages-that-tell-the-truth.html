Reliability

Status Messages, PHD2 Guiding and Tracking Charts Fixed

Version 1.4.6 PRO corrects status messages that did not match the actual state of the system. The interface was tested for a week against simulators and a real PHD2 instance. Fixes include detection of a lost mount connection, guide errors shown in the correct unit, five tracking charts that never drew, and machine-learning screens that showed “Active” whenever tracking was running.
By Bogdan • October 3, 2026 • DEV LOG • v1.4.6 PRO

Status messages such as Connected, Active or Guiding are relied on by users who do not then check the hardware directly. An incorrect status message can therefore cause more trouble than an error that is reported.

For this release the whole interface was tested for a week against simulators and a real PHD2, with the specific aim of finding messages that did not match the actual state. Most of the issues found were incorrect messages rather than crashes.

Lost Mount Connection

If the mount disconnected during a session — unplugged, rebooted, Wi-Fi lost — the application kept showing Disconnect, with frozen coordinates and no message. It now reports Lost contact with the mount, with the reason, within about fifteen seconds. The coordinates are shown as unavailable, and the application reports when the link is restored, or when the driver has restarted and must be reconnected.

Related fixes: Refresh no longer reports Connected for a mount that cannot be reached. A failed connection reports its cause — refused, no answer, unknown host — instead of a generic checklist. The log file no longer receives an error every second: in one test a disconnected mount had produced 430 log lines, and it now produces 13.

PHD2 Connection Delay

Connecting to PHD2 blocked the application for ten seconds on every connection. A byte-order mark at the start of the first request caused PHD2 to reject it, and the application then waited for its own timeout. Without the mark, the connection takes about a tenth of a second.

The existing test server used a standard stream reader, which removes the mark automatically, so the problem was only reproducible with the real PHD2.

Guide Errors in Pixels, Not Arcseconds

The guide RMS value never changed. The application requested a statistics method that PHD2 does not provide; the RMS is now computed from the guide steps.

In addition, guide errors were labelled as arcseconds although PHD2 reports them in pixels, so every value was understated by the pixel scale — by a factor of 4.3 on a 176 mm refractor setup. They are now converted with PHD2’s own pixel scale, and the unit is displayed. The PHD2 panel also has a new guide-error graph, and the guide star PHD2 is tracking is shown live in the guide-camera feed, with a star lost state.

PHD2 reports guide errors in pixels; they are now converted with PHD2’s pixel scale and shown with their unit. On guide errors that were 4.3 times too small

Tracking Charts That Did Not Draw

Five of the six tracking charts in the Advanced Features window never displayed data. The plot kept an old, empty model; the time window was 0.12 seconds wide; and the vertical axes were fixed at plus or minus one arcsecond.

The charts now draw. The window also reconnects to the tracking controller when it is recreated, loads data recorded before it was opened, and shows the actual applied corrections and altitude-azimuth errors. The session statistics and the Plate Solve tab, which previously received no data, are now fed by the tracking loop.

Machine-Learning Status

The machine-learning screens showed Active whenever tracking was running. They now report whether a model exists, its measured quality, and why it is or is not being applied. Reset now deletes the model.

The training was corrected in four ways. It no longer retrains on every cycle once its buffer is full. It no longer blocks the tracking thread. It now predicts the next step rather than a value that was also provided as an input, which removes a label leak. And it is evaluated on a chronological hold-out instead of a shuffled split, since neighbouring samples in a time series are correlated.

Mosaic Panel Placement from Shared Stars

Mosaic panels are now placed using the stars they share with neighbouring panels. A flipped or rotated camera, and the field rotation of an alt-az mount, are therefore measured rather than assumed. This fixes the automatic stitch after a mosaic sequence, which now averages several frames per panel and uses the configured overlap, and the mosaic mode of the Stacking window, where panels used to be placed on top of each other. A panel that cannot be matched is reported instead of being stacked in place.

The Mosaic Wizard reads the focal length, pixel size and sensor from the equipment profile and camera, sends the panels in the order of the selected pattern, and warns that rotation turns the grid and not the camera. A Stop button now cancels a sequence or a mosaic, and mosaics work with native ZWO ASI and Canon cameras.

Single Instance

The previous release, 1.4.5, included two related fixes. The application could be started twice: a second instance ran alongside the first, the embedded web server moved to another port, and the MCP server for AI assistants failed at start-up with address already in use, so the assistant integration was unavailable without any message. The installer’s Launch option made an accidental double launch likely. A second launch now reports that the application is already running and exits; the automatic restart after a frozen window still works.

Also in 1.4.5: after connecting a native ZWO ASI camera, such as an ASI120 guide camera, the live-view buttons stayed disabled. Both live views now work with a native ASI camera, and a failure to start the video stream is reported instead of showing a black image.

Limitations

No machine-learning model has yet been trained under a real sky in this project, so the corrected labelling has been verified by design rather than with real data. PHD2 guiding was tested against PHD2 itself and a simulated guider, not with a real camera. Neither has been validated in the field.

What Changed

Mount connection monitored and loss reported. PHD2 connects without delay, with a computed RMS and correct units. Tracking charts draw. Machine-learning screens describe the actual model state. Mosaics placed from shared stars. A second launch exits instead of conflicting with the first.

What Didn’t

Nothing has been tested under a real sky. This release was checked against simulators and against PHD2 itself, and its release notes state this.

Errors that are reported are usually found and fixed quickly. This release addressed the other kind: incorrect status messages and indicators that give no sign of a problem. The method was to review every message the program can display and check whether it reflects the actual state.
