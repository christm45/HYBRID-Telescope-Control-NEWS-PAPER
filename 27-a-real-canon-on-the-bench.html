Cameras

The Camera That Took No Pictures, and Reported Success

We connected a Canon EOS 550D to a PC and pressed Start Imaging Sequence. Twenty-five milliseconds later the program announced that the sequence had completed successfully. The shutter had never moved. What followed was a day of finding defects that no synthetic test could have found, because each of them needed a real camera on a real cable.
By Bogdan • October 5, 2026 • DEV LOG • v1.4.7 PRO

Time to Report Success

25 ms
taken by a sequence that captured nothing and reported success

Frames captured: 0. Duration: 00:00:00. Average time per frame: 0.0 s.

The camera sat on a desk, a USB cable running to the PC. It was a Canon EOS 550D, a body widely used in astrophotography. There was no mount connected and, because it was daytime, no sky. That is precisely why the test was worth running: it removes everything except the camera and the program.

The camera was connected, recognised, configured from the sensor database — 5184×3456 pixels, 4.3 µm. Test capture, live view, a change of shutter speed and ISO: all worked. Then we pressed Start Imaging Sequence.

Twenty-five milliseconds later, the program announced that the sequence had completed successfully. The shutter had never moved.

The Trace That Told the Truth

The activity log showed nothing. The window showed nothing. The explanation was not anywhere a user could look. So we attached a listener to the program’s debug output, ran the sequence again, and read what the engine had actually said:

[ImagingSequence] Filter switch to 'L' (pos -1) FAILED - frame 1 skipped.
[ImagingSequence] Filter switch to 'L' (pos -1) FAILED - frame 2 skipped.
[ImagingSequence] Filter switch to 'L' (pos -1) FAILED - frame 3 skipped.
[ImagingSequence] Sequence complete! 0 frames captured

A Filter Nobody Asked For

A sequence without a per-filter plan runs on an implicit entry named “L”, position −1. The engine sent that entry to the filter wheel like any other. Without a wheel connected — which is every DSLR and most ASI set-ups — the window’s handler answers no. The engine, quite reasonably, will not expose a frame through a filter it could not select — the picture would be filed under the wrong name — so it skipped the frame.

Then came the second failure. The engine stops a run after five consecutive failed frames. We had asked for three, so three skips was fewer than five, the loop reached its end, and the result was Success: true, 0 frames.

Both are repaired. The engine now consults the filter wheel only when a real filter plan exists, and a run that captured nothing is never a success: it is reported as failed, with its reason.

The sequence did not fail. It succeeded at doing nothing, and reported the success. On an engine that counted skips as progress

A Camera on Its Own

The next run stopped just as fast, for a different reason. With no mount connected, the meridian-flip check answered unknown, and the engine turns unknown into an abort “to protect the telescope”. A camera on its own has no telescope to protect. Now a mount that was never connected means there is nothing to flip; only a mount that was connected and then lost is genuinely unknown.

That abort had also been invisible. The engine reported its end to the window only through its normal exit; an exception, a validation error or a cancellation raised inside a capture all returned a failed result to a caller that never looked at it. The screen stayed silent and the Start button stayed grey. Every exit now reports.

RAW That Was Not RAW

With the sequence running, the files that came back were JPEG. The program asks the camera for RAW by setting an image-quality code, and the code was wrong: 0x00640F0F where Canon’s own header gives 0x0064FF0F. The camera refused the setting; the refusal was ignored; and a user who asked for RAW received a JPEG every single time. The code is corrected, and a refusal is now recorded rather than discarded.

73 Seconds for a 35-Second Exposure

A 35-second bulb exposure took 73 seconds to arrive. The explanation is almost certainly a camera feature: after a long exposure, the 550D can record a dark frame as long as the exposure itself — its long-exposure noise reduction — before it sends anything.

The program waited for the image for a fixed 60 seconds. Any exposure beyond about a minute would have lost its picture. The wait now grows with the exposure, and the estimated time shown before a sequence counts the dark frame: 35 seconds is announced as about 80 rather than 45, against the 73 measured. If a body has the noise reduction switched off, the estimate is a little pessimistic, which is the right way round.

A Decoder That Says No

To measure focus and to solve plates, the program must read the camera’s RAW file. Canon’s SDK refused every attempt to develop the 550D’s file at full size — error 7, not supported, in every output format we tried — while decoding the 160×120 thumbnail without complaint. We could not establish why.

Every Canon RAW file also carries a full-size JPEG rendering of the picture. That is what the program now falls back on: eight bits instead of fourteen, which is ample for a focus metric or a plate solve.

The Window That Closed the Application

One defect was in no way about cameras. After a forced close, the next start shows Interrupted Session Detected. Whichever button was pressed, Resume or Start Fresh, the entire application then quit.

The cause is a rule of the framework. The application is set to exit when its main window closes, and the first window created is taken to be the main one. The recovery dialog is created first. Closing it ended the program. It is now held open under explicit control and forgotten as the main window as soon as it has answered.

Smaller Things

The live view on the Tracking tab was paced on the shutter speed, which gave 0.8 images a second at a one-second exposure where the camera’s own stream delivers about six. It was labelled an ASCOM camera, and its footer went on naming the camera after Disconnect. The Cancel button of the camera-type chooser was cut off at the bottom of its window. All four are fixed.

What We Did Not Test

There were no stars in the room. The frame-quality scorer gives a score of zero to a picture without stars, so it asked for each frame twice; and the debug build used for the test has no embedded Python, which the scorer needs. A real sky, with a focuser and a mount, is still to come. The 500D, 600D and 700D bodies are untested, and the installer has not yet been run on a clean machine.

What Changed

The filter wheel is consulted only when a filter plan exists. A run with no frames is a failure. No mount means nothing to flip. Every exit of the engine reports. RAW is RAW. The download wait grows with the exposure and the estimate counts the dark frame. A JPEG fallback when the SDK declines the RAW. A recovery dialog that no longer ends the program.

What Didn’t

A sequence that has a real filter plan still skips a frame when its wheel fails, and every stacking result is untouched. The new engine tests fail on the old code and pass on the new, and the full suites are green.

A test suite cannot tell you that a button does nothing, or that a camera has been asked, politely, for the wrong file type. The camera on the desk can. It was connected in the first minute and it spent the rest of the day telling us what the software had been getting wrong.
