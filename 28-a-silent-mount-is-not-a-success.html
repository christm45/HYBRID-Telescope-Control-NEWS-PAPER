Reliability

Unanswered Mount and Accessory Queries No Longer Treated as Completion

A session log showed “Slew completed” for a slew that had just been aborted. The cause, found in many places in the code, was that a mount which did not answer a status query was treated as a mount that had arrived. Version 1.4.10 PRO fixes this for the mount and for the focuser, rotator, filter wheel, dome and flat panel.
By Bogdan • October 13, 2026 • DEV LOG • v1.4.10 PRO

Slew-Status Call Sites

19
call sites that ask whether the mount is still slewing

Most of them treated an unanswered query the same as “no”. The ones that determine the next action — plate solve, sync, flip, imaging — are fixed in 1.4.10.

The scope of this review was the interface, the connections and the settings, with the aim of finding communication errors with the mount and accessories. It started from the log files of real sessions, followed by a reading of the code behind every message that looked incorrect.

The Session Log

One session ended with an abort during a GOTO. Shortly afterwards the log reported that the slew had completed, although the mount had been told to stop. The program then continued as if the mount had arrived: it took an image, plate solved it and synced the mount’s pointing position.

Three Possible Answers

The wait loop asks the mount whether it is still slewing. The answer can be yes, no or nothing, because the link can fail; after two failed attempts the wrapper returns nothing. The loops were written as “keep waiting while the answer is yes”, so nothing ended the wait in the same way as no.

while (slewing == true) wait();   // nothing  =>  stop waiting
announce("Slew completed");

The effect is most serious where it is least visible. A mount that has lost its link is treated as a mount that has arrived. A plate solve then compares the sky with a position the telescope never reached, and a sync writes the difference into the mount as a pointing error.

An unanswered status query does not indicate that the slew has finished; the mount’s state is unknown. On the slew-wait loop

The Fix

The mount wrapper now records an abort, and a wait loop that sees one stops with a warning and does not sync. A single unanswered query is tolerated, since drivers occasionally fail to respond; three in a row are treated as a lost link, and the operation stops with that message. The same rule now applies to the scheduler’s slews, its meridian flip, dithering, the re-slew after a sync, the flip on the Imaging tab, Center-and-Rotate, three-point polar alignment and Just-Go.

Interface Blocked While Waiting for the Mount

Two buttons — the sub-exposure calculator and the start of an imaging sequence — requested the focal length from the mount and blocked the interface thread until it answered. The mount’s timeout is ten seconds, so with an unresponsive mount the window froze for ten seconds per request. These requests are now made without blocking the window.

Accessories

The same type of defect was found in the accessory code, in three forms.

Timeout reported as success. The focuser waited sixty seconds for a move to finish and then reported Move complete, even when the motor was still running. It now halts the focuser and reports a timeout.

Error read as “finished”. The rotator’s IsMoving returned false when the driver threw an exception, which was interpreted as a completed move. Three failed reads in a row are now an error and the rotator is halted. Its fallback to a second move type, intended for drivers without a mechanical move, also ran on any driver error and could therefore start a second movement; it now runs only when the driver does not implement the method.

Wait ending before motion starts. The filter wheel returned as soon as it saw no motion, which could be before the motion had started. It now waits until the wheel reports the requested slot, and stops waiting promptly if the driver stops responding instead of waiting thirty seconds. The dome’s park and find-home, its shutter, and the flat panel’s cover had the same race condition and now confirm the expected state. A flat panel that never reports ready is now an error, instead of a series of flats being taken with the panel off.

Derotator Defaulted to Longitude Zero

The field derotator read the site latitude and longitude from the mount. When the longitude could not be read, it used zero — Greenwich — without a warning, and rotated the camera on that basis. It now refuses to start and reports why. Stopping the derotator also halts a rotator that is still moving, and the loop warns after five cycles without a position from the mount.

LX200 Connection Without a Reply

The LX200 driver’s Connect opened the serial port, sent a product query and returned success even if nothing replied, so any open COM port was accepted as a mount. It now fails when the query is not answered, and releases the port.

Testing and Limitations

For the focuser, rotator and filter wheel, a small simulated driver was written. The rotator and filter-wheel tests fail on the old code and pass on the new, covering an unresponsive driver, a move that never ends, and a wheel that reports the old slot. The GOTO loops, the scheduler and the flips are covered by tests that inspect the source code, because exercising them requires a window or a serial port. The full test suite passes.

These tests do not cover the behaviour of a real mount whose link is cut during a slew. The dome and the flat-panel cover have no behavioural tests. The polling timers of the focuser, rotator and filter wheel still read their drivers on the interface thread, because the drivers are created there and moving them is a larger change. A driver that hangs can still freeze the window.

What Changed

No response from the mount now stops a GOTO, flip, dither or polar alignment instead of completing it. Aborted slews are never synced. Focuser, rotator, filter wheel, dome and cover moves are confirmed or halted. An unreadable longitude stops the derotator. An LX200 that does not answer is not reported as connected.

What Didn’t

No test was run on a real mount with its link cut. Polling for three accessories still runs on the interface thread. Stacking, calibration and image results are unchanged.

The program can only act on what the hardware reports. When the hardware does not respond, 1.4.10 now reports the missing response instead of assuming success.
