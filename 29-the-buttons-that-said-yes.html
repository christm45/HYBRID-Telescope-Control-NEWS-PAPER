Audit

The Buttons That Said Yes

A full read of the program, interface and code, by six independent reviewers. The worst finds were not crashes. They were buttons that reported success and did nothing, and settings that were quietly ignored.
By Bogdan • October 25, 2026 • DEV LOG • after v1.4.11 PRO

The Audit in Numbers

~25
high-severity findings, each checked against the code

Six reviewers each took one part of the program: the interface wiring, the mount and tracking, the cameras and sequences, stacking, the web and voice services, and the rest of the interface. Every test suite was green before the audit started — which is the point.

The request was short: audit the whole program, interface and code, and report anything that does not work. The test suites passed before we began: 1,016 interface tests, 574 image-processing tests, all green. They did not see any of what follows, because almost none of it throws an error. It says yes.

The Scheduler Shot Through the Guide Scope

The Target Scheduler was given the program’s first camera object, which is the guide and plate-solve camera. With a native ZWO or Canon imaging camera, every target failed with “camera not connected”. With an ASCOM guide camera, the lights were taken through the guide scope. It also always shot at bin 1, and a second run on the same evening overwrote the first run’s frames, because the default file name had no time in it. The scheduler now uses the imaging camera, honours the binning, and never overwrites a frame.

Three Buttons That Did Nothing

Apply to Sequence showed “Target schedule applied to imaging sequence!” without reading a single target. RUN PLAN asked for confirmation that “the scheduler will start immediately and run unattended”, then stored the plan and logged that it was ready. And the Night Plan window could not show any plan at all: one drawing element was added to two parents, which WPF refuses, so every non-empty plan ended in “Plan generation failed”. An empty schedule, meanwhile, was silently replaced by five sample Messier targets.

Apply now hands the schedule to the scheduler queue. RUN PLAN opens the scheduler with the plan’s targets and starts it — after giving it the observing site, which an independent review of the fix showed was still missing in its first version. The sample targets are gone.

A button that reports success is making a claim. Most of these claims were never checked by anything. On the dialog that applied a schedule it had not read

“31,94” Seconds

Windows in Serbia, France or Germany writes decimals with a comma. The scheduler read right ascension with a parser that treats a comma as a thousands separator, so 05:34:31,94 became 3,194 seconds — and that was the slew target. The same family of defect zeroed a pixel size of “4,63” in the equipment profile while the dialog said “saved”, sent “1,23” to the quality analyser’s Python, and built the Gaia query for colour calibration as CIRCLE(’ICRS’, 123,45, 41,27, 2), which Gaia rejects. On a comma-decimal Windows, colour calibration could only ever report “0 catalogue stars”. All of these now accept either separator, and every number sent to another program is written with a point.

The Pier Side, Measured

When a mount cannot say which side of the pier it will use, the program falls back to a rule: past the meridian and still on the pre-flip side, the flip is due. The rule tested the wrong side. Rather than argue from documentation, we asked the ASCOM simulator: two hours east of the meridian it reports pierWest, two hours west it reports pierEast. The old test answered “not due” while the telescope tracked towards the pier, and “due” again right after a good flip. It now uses the measured convention. The same probe confirmed that the declination-axis sign used by the tracking loop was already right.

Stacking: the GPU Box Was a Filter

The “GPU acceleration” box is ticked by default. The GPU route only implements the final combination, so with it on the program silently skipped drizzle, normalisation, quality weighting and automatic rejection, stacked “Sum” as a mean, and for median and sigma-clipping used only the first 256 frames — while reporting every frame as accepted. Settings the GPU cannot honour now go to the processor instead. Local normalisation had its own fault: in a tile of empty sky it fitted a slope to pure noise and clamped it to 0.1, scaling each frame’s own data down by a factor of two to ten. It now matches each tile by median and spread.

The Tunnel and the Empty Password

The remote-access tunnel wrote a log line for every connection into a pipe nobody read; once the pipe filled, the tunnel froze while still reporting itself as running. It is now drained, and the tunnel, like the MCP server, is closed with the program even after a crash. A damaged settings file could also leave the web credentials empty — and an empty user name and password then matched each other. Empty credentials now never authenticate, are regenerated and saved, and the file is written atomically.

How We Know

Each fix has a test that fails on the old code and passes on the new, and we checked that it fails: 22 tests for this first group. A second, independent review read only the fix itself and found four mistakes in it — among them the missing site, Canon RAW files that would have been renamed .fits, and two scheduler sessions able to run at once — all corrected before the commit. The full suites pass, including 18 tests on 564 real NGC 2903 frames.

What Changed

The scheduler uses the imaging camera. Apply and RUN PLAN do what they say. Comma decimals are read correctly. The fallback flip rule matches the measured pier sides. The GPU route no longer drops settings. The tunnel stays alive, and empty credentials never open it.

What Didn’t

None of this has been under a real sky yet. These fixes are in the source and will ship in the next installer; v1.4.11, online today, does not contain them.

A crash announces itself. A button that says yes and does nothing waits for a clear night to be found. This audit tried to find them first.
